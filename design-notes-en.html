01 · NO.02

Chrono Loop — a time-loop puzzler

Game designCompletedUnityC#Aseprite

Overview

A Unity time-rewind puzzle built end to end by one person — concept, mechanics, code and pixel art. Rewind is not a power-up bolted onto a puzzle; it is the loop the whole game stands on.

Build

Paper prototype first, only to pin the rules: how far back can you rewind, which state survives the jump and which resets. Every later level depends on those answers, and answering them on paper is what keeps a cool-sounding mechanic from playing hollow.

Then the Unity + C# rewind system, with art drawn frame by frame in Aseprite so mechanics and visuals share one language. Difficulty climbs by cognitive load rather than by damage: single rewind teaches the rule, later rooms stack multi-segment rewinds with moving platforms. Ghost trails, audio and result screens carry the feedback load, so a failed attempt reads as information instead of punishment.

Design reasoning

The loop I wanted is fail → rewind → retry as a gain, not a loss. Traditional puzzling asks you to be right once; this asks you to explore. That permission to experiment is the emotion the time-loop premise is actually good at carrying.

Retrospective

It proved one person can carry design through to finished art. The obvious next step is widening the rewind target: from rewinding the character to rewinding the world — enemy positions, mechanisms, the state of the room.

02 · NO.03

AI-assisted side-scrolling roguelike

Game designCompletedPythonPygameBehaviour treesTrello

Overview

A four-person Pygame roguelike. I led the project and owned two systems: enemy AI and dynamic difficulty.

Build

On the management side, Trello carried the milestone plan, with tasks cut fine enough that dependencies between code, art and design were visible before they became blockers. We shipped a complete playable build on schedule.

Enemies run on behaviour trees with patrol, chase, attack and flee states, selected from live signals like player distance and health. Difficulty follows the player instead of a fixed curve: health, miss rate and clear speed feed adjustments to enemy density and attack frequency.

Design reasoning

Difficulty should track performance, so a newcomer is not pushed out and a veteran is not bored. A behaviour tree is what makes that safe to tune — the enemy stays predictable in shape while varying in behaviour, so difficulty can move without the encounter turning random.

Retrospective

Playtests supported the adaptive approach. The bigger takeaway was organisational: on a four-person team, how you organise people matters as much as how you write code.

03 · NO.04

Blender 3D still-life study

Visual researchCompletedBlenderCyclesPython API

Overview

A 3D tabletop still life. I owned the core models, the translucent shader work and the render pipeline, with Python scripting around all of it.

Build

Blockout first — proportion, structure and silhouette carry the frame, so composition got settled at low detail before any modelling hours were spent. Glass and liquid were the hard part: transmission and refraction stacked through layered shader nodes, then re-lit repeatedly until the material read as clear rather than grey.

Blender's Python API handled scene assembly, camera path animation and batch rendering. The mechanical, repeatable work went to the script; the judgement work — lighting, material, framing — stayed manual.

Design reasoning

Procedural where the work is repeatable, hand-made where it needs taste. That split is the most comfortable way I have found to work in 3D, and it holds for any scene project afterwards.

Retrospective

This is where Blender's Python API and the Cycles pipeline became fluent rather than familiar. The reusable part turned out to be the automation, not the asset.

04 · NO.05

Android touch Snake

Game designCompletedKotlinAndroid StudioTouch input

Overview

Snake rebuilt for phones, solo, in Kotlin. The actual brief was narrower than "port a classic": a game designed around precise timed turns has to survive a finger.

Build

Kotlin framework, full core logic, multi-scene audio and a working grip on Activity lifecycle and resource handling. Swipe steering, collision against walls and the snake's own body, pause and scoring all landed in the first pass.

The second pass was entirely feel: judgement windows and sensitivity retuned against gesture latency so the snake reads as following the thumb instead of lagging behind it.

Design reasoning

Keyboard Snake rewards timing precision measured in frames. Touch cannot deliver that, so the fairness has to move into the input layer — a wider judgement window and forgiving sensitivity, rather than a one-to-one key map onto glass.

Retrospective

A complete Android pass: syntax, lifecycle, resources, packaging. It closed the mobile line on my skill list rather than leaving it at "read about it".

05 · NO.06

YOLOv8 car-model recognition

Visual researchCompletedPythonYOLOv8OpenCVONNX

Overview

Real-time recognition of one specific car model (Xiaomi SU7) on resource-limited edge hardware.

Build

1,100 images built by a positive/negative strategy — 700 of the target, 400 of near-identical sedans — split 90/5/5. Two models compared under identical conditions: YOLOv8n at 3M parameters against YOLOv8s at 11M, 640×640 input, 300 epochs.

n won on value for this data size. Export to ONNX removed the framework dependency and left a cross-platform deployment path.

Design reasoning

The negatives are the design. Training on "car vs. not car" produces a detector that fails on the only question that matters — this sedan or the sedan next to it. And on an edge device, latency and deployment cost are the hard constraints; accuracy only has to clear the bar.

Retrospective

Data construction, model comparison, lightweighting and ONNX deployment as one chain. The lesson that stuck: data quality and deployment constraints decide outcomes more often than architecture does.

06 · NO.07

RTSP streaming server, from scratch

Interactive mediaCompletedPythonSocketsRTSP / RTP / SDPThreading

Overview

A multi-client RTSP server written without leaning on an existing library: protocol commands, session handling and concurrent streaming all implemented directly.

Build

Five core commands — OPTIONS, DESCRIBE, SETUP, PLAY, TEARDOWN — implemented against the RFC state machine. Each session generates its own conformant SDP description, so clients stay isolated from one another.

Sockets plus threads for concurrency. Verified in FFplay and VLC: under 200 ms latency at a stable 30 fps with multiple clients attached.

Design reasoning

Protocol before code. Drawing every legal state transition first is what separates "it plays a video" from "it is a server". Per-session SDP is the line between a demo and a toy built for one client.

Retrospective

The streaming stack — RTSP, RTP, SDP — and threaded network code, learned by having to satisfy them. Protocol compliance is a quality floor in systems work, not a feature.

07 · NO.08

Chrono Loop Web — rewind prototype

Interactive mediaPlayableHTML5 CanvasJavaScript

Overview

The rewind mechanic from Chrono Loop rebuilt as a browser-playable prototype, so the fail-rewind-retry loop can be felt in thirty seconds without installing anything.

Build

State is written per frame into a five-second ring buffer — a replayable history with no save system attached. Death auto-rewinds 2.5 seconds at double speed; R rewinds three seconds by hand. Ghost trails and backflowing particles make the reversal visible rather than merely functional.

Levels include a moving platform, spikes and an exit. Edge cases that surfaced during play were fixed rather than documented: history exhaustion, stuck keys across resets, plus on-screen buttons and canvas scaling for mobile.

Design reasoning

A ring buffer, because "the last few seconds" is exactly the retry window — a full save system would be overkill for the same effect. Two rewinds, two rhythms: automatic for rescue, manual for intent. Everything else serves one goal, that the core loop is legible on first contact.

Retrospective

The mechanic works on the web. What the prototype really taught is that boundary states — empty history, held keys — have to be designed in a rewind game, not discovered later.

08 · NO.09

XV6 MLFQ scheduler + visualisation

SystemsCompletedCXV6 kernelMLFQPython viz

Overview

Undergraduate thesis: a multi-level feedback queue scheduler implemented from zero inside the XV6 teaching kernel, replacing the default round-robin, with experiments run against real scheduling logs.

Build

Process control blocks extended in proc.h / proc.c / trap.c with three fields — queue level 0–2, ticks in queue, wait ticks. The scheduler was rewritten for three priority queues: new processes start in Q0, CPU-bound processes demote when the quantum expires, I/O-bound processes keep their level by yielding often.

A timer-driven anti-starvation pass keeps the bottom queue from dying. Then a Python visualisation framework turned kernel logs into Gantt charts of demotion and comparison bars of retained priority — the experiments were read off real runs, not simulated.

Design reasoning

MLFQ is priority set by observed behaviour instead of by declaration, which is what buys responsiveness without giving up throughput. And a scheduler's correctness is not a matter of opinion: the log either shows the demotion or it does not.

Retrospective

Interactive processes responded measurably better than under round-robin. It is the closest I have come to operating-systems theory as working code, and the project that made the bottom of the stack feel concrete.

09 · NO.10

Monogatari lore map

Interactive mediaPlayableHTML5SVGData visualisation

Overview

A research piece on an anime series rebuilt as a navigable space rather than an article: one character's journey timeline, a draggable relationship graph, and the 2012–2019 series timeline.

Build

Every fact traced through Japanese primary sources: eight main characters, their order of appearance, how they connect, and the key story beats across the series run. Eight portraits act as shortcuts into the relevant section.

Three views, three questions — what this character went through, how these characters relate, how the series evolved. The relationship graph is draggable SVG with live edges and a layout reset. Single HTML file, portraits embedded, works offline.

Design reasoning

Long-form research decays into forgotten paragraphs. Turned into a map, the reader moves by curiosity and sets their own route — and the three views exist because those three questions kept getting tangled in prose.

Retrospective

This one was information architecture, not content. Once the material is big enough, how you structure the views and guide exploration outranks how much you put in.

Global game-sales dashboard

Interactive mediaPlayableEChartsData visualisationResponsive

Overview

An interactive dashboard over 16,327 titles that sold 100,000 copies or more between 1980 and 2020, built so a reader can slice the market themselves instead of reading someone else's summary.

Build

Cleaning and shaping the dataset came first, and the counting rules are stated in the page footer — every figure on screen can be traced back to a definition. Three filters combine: year range, region (North America / Europe / Japan / other) and twelve genres, with every KPI and chart re-rendering on change.

Five chart types cross-reference each other: stacked area for yearly trend with a toggle to split lines, a donut for regional share, bars for genre comparison, a platform ranking. Dark theme, responsive layout.

Design reasoning

"How much did Japanese action games sell in the nineties" has no preset answer page — the filters are the answer. Cross-referencing charts is how a pattern that is invisible in any single view becomes legible.

Retrospective

Practice with ECharts state sync and responsive dashboard layout. The habit that came out of it: state your data definitions where the reader can see them.

11 · NO.12

Pulsar Field — playable soundscape

Interactive mediaPlayableWeb AudioCanvas 2DGenerative

Overview

A generative instrument disguised as deep-space instrumentation. Click or drag the night sky and it answers with stardust particles and synthesised notes: horizontal position sets pitch, vertical sets velocity.

Build

Pitch is mapped across an A-minor pentatonic scale, velocity across vertical position, with four colour phases rotating by note — position, colour and sound sharing one coordinate system. Every sound is synthesised in Web Audio with no samples, across four timbres.

A 92 BPM generative composer runs an i–VI–III–VII progression with kick, hats, bass and melody scheduled by audio-clock lookahead, so audio and visuals stay locked. Single file, no dependencies: mute always reachable, reduced-motion respected, touch supported, plus a silent ?demo=1 preview so the page can be screenshotted or reviewed without sound.

Design reasoning

Pentatonic because any click has to sound good — no black keys, no wrong notes. Lookahead scheduling because drifting audio clocks destroy rhythm. The piece is an instrument, not a player: your gesture produces the sound rather than triggering a pre-recorded phrase.

Retrospective

Zero-sample generative audio works on the web, and this is where audio scheduling, pitch mapping and audio-visual sync stopped being abstract.

Stardust Catcher — arcade collection

Game designPlayableCanvas 2DWeb AudioParticles

Overview

A one-screen arcade loop: catch falling stars in a bubble, bank combos, take the risk for a rare cyan star, and lose a life to a red meteor.

Build

Gold stars build combo and score, cyan stars pay a large bonus, red meteors cost a life. Spawn density and fall speed ramp with play time, so difficulty rises without a scripted curve.

Every catch pays out in several channels at once: a suck-in animation, a particle burst, screen shake, and a score multiplier every fifth combo. Music and effects are synthesised live in Web Audio, the best score persists in local storage as something to beat, and ?demo=1 runs an unattended preview.

Design reasoning

One-sentence rules, dense feedback — the arcade recipe. The combo multiplier and rare stars add the hook that turns casual catching into light optimisation: there is a best route, and it is worth chasing.

Retrospective

A second pass on procedural audio and particles after Pulsar Field, with a tighter feedback loop. It also confirmed that a single-file, dependency-free build is the right shape for portfolio work — it opens and plays anywhere.

13 · NO.14

Branch Road — LLM branching narrative

Game designPrototypeglm-4-flashedge-ttsCogViewTTS

Overview

Vertical slice 0.1 of a narrative game where the branches are generated live by an LLM. The question it exists to answer is whether instant generation can carry immersion, not whether it can produce text.

Build

A fixed frame carries four planted clues — the last train, Lin Wan's phone, a 23:47 scheduled draft, the terminus — and the narrator never spells any of them out. Options are generated per turn alongside free-text input, and eight turns reach an ending, after which the player can revisit the ending their other choice would have produced.

At the terminus the 23:47 letter appears as a card and is read aloud by an edge-tts voice; eight CogView scenes are pre-generated so the visuals switch with no wait. Instrumented probes record whether players want to know what the other choice held — the design claim tested against real play.

Design reasoning

Fixed frame with live branches is the pragmatic trade: the frame guarantees a quality floor, generation guarantees that no two runs match. Free-text input matters because choosing among four prepared options is a quiz, while typing an action is acting.

Retrospective

Generation can hold immersion at viable cost, and the hybrid — human frame, machine branches — is the version that holds up. The probes also showed that instrumented design works in narrative games, not only in systems.

14 · NO.15

Room of Choice — 18 endings

Game designPlayableJavaScriptZero dependencyBranching narrative

Overview

A pure-front-end narrative game: four chapters, eighteen endings, eighteen clues, no build step — double-click and play. All content is config-driven and the engine never changes.

Build

The structure carries the complexity: a chained two-clue true ending in chapter four, a true-ending epilogue that revisits the foundation, trap gates that imitate endings, a fake exit that loops, and merge points where branches rejoin a trap.

Two codexes — clues and endings — with progress saved locally, plus divergence hints, turn collection into a reason to replay. A "run regression test" button checks the whole story graph on demand, so an eighteen-ending structure cannot quietly break.

Design reasoning

Multi-ending narrative is a graph: scenes are nodes, choices are edges, traps and true endings are part of the structure, not exceptions to it. Treating it that way makes the content measurable — you can see how much of the graph a player has walked — and testable, which is what stops branching from becoming hand-maintained contradictions.

Retrospective

Content in config, engine untouched, is what let writing and building separate cleanly. The general lesson: narrative complexity has to be absorbed by structure, because hand-written branches scale linearly and then collapse.

Living — generative ecosystem

Interactive mediaPrototypeGenerative audioAutonomous agentsHTML5

Overview

An interactive media piece built on autonomous evolution and generative sound: a colony of organisms lives, grows, reproduces and dies on its own, while the player supplies energy and nudges direction.

Build

Colony behaviour runs on rules — birth, growth, reproduction, death — producing a small ecology that keeps running with nobody at the keyboard. The player never controls an individual; moving and clicking injects energy that bends the direction of growth.

Sound is generated from colony state in real time, so a thriving colony literally sounds richer. Four viewing modes, a mute key and pause let a visitor choose between watching and taking part.

Design reasoning

The design question was what role the player holds in work about life cycles. Not an omniscient controller — an energy source inside the system. Your presence changes where it goes; it does not decide what each organism does. That is a more interesting position than protagonist, and it leaves room for the piece to say something.

Retrospective

An experiment on the player's role in interactive art, and the result surprised me: released control still produced strong participation. It also set a direction for later interactive-media work.

Co-Desk — networked study desk

SystemsCompletedElectronReactFastAPIWebSocketSQLite

Overview

A runnable MVP from an HCI course: an Electron + React desktop client against a FastAPI backend with SQLite persistence, turning "studying alone is lonely" into a product two people can actually share over the internet.

Build

Room lists and custom rooms, account registration with hashed passwords, a pomodoro timer, task notes with breakdowns, ambient audio with seat-direction preview, encouragement cards, focus statistics and a study-time leaderboard. The backend is designed to sit on a cloud host from the start — HTTPS REST plus WSS — and the client only needs the server address to sync a room across devices.

Verification used a two-client simulation script driving ten live assertions: join, peer list, state sync, heartbeat, broadcast, leave and fallback. All ten passed, and a win-x64 build was packaged for distribution.

Design reasoning

The target was companionship, not chat. Seats, focus state and live progress are the social signals — being in the same room has to be perceptible without talking. Making "cloud-hostable backend" a constraint on day one is what avoided the local-single-machine trap that MVPs usually fall into.

Retrospective

Full-stack in one pass, through the HCI method of observation, prototype, runnable product. Next steps would be real spatial audio over WebRTC and a PostgreSQL migration; both are deliberately out of MVP scope.

17 · NO.18

Conversation Archive — AI summary MVP

SystemsPrototypeHTML5OllamaLocal LLMlocalStorage

Overview

An interactive MVP for a feature every AI product needs: turning a long conversation into structured takeaways. Every takeaway is clickable back to its source sentence, deletable and regenerable. A privacy toggle and a local model keep the transcript on the machine, and the archive view turns summaries into searchable memory.

Build

Before building, the feature was scored on five axes — user pain, frequency, cost, effect, side effects — and the verdict was "build it, but start manual". Auto-summarising changes behaviour and can silently drop detail, so a manual trigger was the right scope for P0: one conversation, three tiers of takeaway, source anchors, an explicit "AI-generated, may be wrong" label.

The engine degrades twice: local Ollama running qwen3:8b with output constrained to strict JSON first, then a browser-side rule summariser (keyword and sentence-length scoring) when the model is absent or privacy mode is on. P1 added background archiving on conversation switch and model-generated titles. P2 added the archive library: cross-session search with hit highlighting, aggregation by conversation, jump-back links.

Design reasoning

Accuracy and privacy are the two lifelines of a feature like this. Anchors make a wrong model output checkable rather than authoritative; the privacy switch hands the compliance decision to the user. The degrade chain — real model, then rules, then demo data — means a review never ends in an empty screen, which is itself part of the argument for shipping it.

Retrospective

Verified rather than asserted: seventeen parser unit tests, six takeaways from the real model with every anchor inside the transcript, zero console errors in page checks. The conclusion is a scoping one — a demonstrable, degradable, offline-capable AI feature gets further than a complete one.

18 · NO.19

Mometa (UE5) — hand cards and difficulty

Game designIn developmentUE5 / UMGHi-fi prototypeAutomated acceptancePer-floor sampling

Overview

A hand-card iteration in a UE5 card game, and the most complete problem → prototype → verification → trade-off chain in my work. The starting problem: in a 1,180 px row, eight cards show 147 px each, so names and numbers cannot be read. Scattering them across the table would fix that — but "position equals index" is the spatial memory players rely on by turn three. Whether scatter destroys blind play is what the iteration had to settle.

Build

An HTML hi-fi prototype settled the layout first: a 4×2 grid for spread plus jitter for non-alignment. Pure random placement piled all eight into one clump — a pit found at prototype stage, along with rotated bounding boxes clipping the table edge when only half a card of margin was left.

In engine, pose data FHandCardPose{X,Y,Angle,Z} lives on the card, so position comes from the card rather than from its index. Action grammar: click flips (ScaleX squash-and-swap, no fake 3D), double-click plays, drag flicks out with 80 ms velocity sampling, landing prediction and a 700 px/s threshold. Selection overlay, cancel-return and hover-lift were all rebased on the pose, otherwise the overlay snapped back to the old row position.

Six acceptance steps A1–A6 — pose consistency, flip chain, slow-drag return, fast-flick destroy, collapse to zero — feed coordinates into the same StepDrag / HandlePress / HandleRelease the game runs. 6/6 passed, and they caught two bugs a human would hit: rapid clicks swallowing a card (fixed with a flip queue) and a refresh breaking a drag mid-flight (drags voided in SetHand). A pose guard keeps a same-hand refresh from re-scattering.

Version v77e moved scatter out of the permanent state: hold Tab to spread the hand, release to return to the row, play always happens in the row. Flicks in inspect mode now return to the deck instead of tearing, since inspect is for reading and one stray flick should not cost a card. The same six steps were re-run in the inspect state: 6/6.

Tearing became the carrier of resource pressure rather than a punishment animation. One battle, one deck: played cards tear and are not recovered, free discards are removed, and the only release valve is "hand over eight returns to deck". The deck is restored whole after the fight with card count conserved, and an extreme-build fallback prevents a first-floor stall. Off-screen cards are eaten by the board — the cost is a card in the build, not health.

Difficulty was resampled, not felt. Fixing the map bug revealed the first run dying on floor 8 of the final chapter, a chapter that had never been run against the real enemy pool. Draw counts were isolated behind a pinned-start switch: at one card per turn the final chapter lost four of four, at three cards it cleared three of four, so the curve became 2/3/3. The same pass found two contradictory draw configurations and collapsed them into one source that warns on mismatch. Then win rate alone stopped being useful evidence — the hard point had moved from the final chapter to the first, where the boss broke four of four runs but left players at a dozen health with no recovery window after the map change. Measurement switched to per-floor sampling: entry health, turn count and post-fight health, normalised against the character's maximum into a curve, and tuned only where the curve actually dips. The tightest stretch went from cliff to slope, the lowest entry point rose more than a dozen floors, and first-two-turn deaths went to zero.

Design reasoning

Scatter was rejected by numbers, not by feel: only three or four of eight cards were genuinely readable across a 1,400 px spread; per-turn reshuffles erase spatial memory, which means re-reading the whole table each turn; the click was already spent on flipping, so the detail overlay got skipped; and "flick equals permanent tear" punished the highest mis-touch action in the whole scheme. But the scatter itself was good — the angles and overlaps really do look like a table, and the action grammar is richer than a row. So the idea was not deleted, it was split: the pretty state appears on demand, the usable state is always there. The same logic graded the penalty — a flick in inspect returns to the deck, a flick in play tears — because the meaning of the gesture should set the cost.

Retrospective

Boundaries recorded honestly: the Tab-to-InputComponent binding cannot be verified without keyboard automation, so a right-click fallback exists pending a human pass; drag feel is code-complete but human flick testing is outstanding; eaten cards have no fly-out animation, which needs incremental rebuild. On method: the value of automated acceptance is not that it passes — it is that the two bugs it caught are exactly the ones a human produces by clicking fast or refreshing mid-drag. The script translated feel problems into reproducible assertions.

One limit worth stating plainly: every sample here is a bot, zero human runs. These curves are the ceiling under ideal execution, not human win rates.
